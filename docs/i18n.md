# Bilingual Documentation Guide / Guía de Documentación Bilingüe

## ES

### Por qué bilingüe

Este proyecto usa documentación bilingüe español-inglés (ES/EN). El español va primero porque refleja el idioma nativo del maintainer y la audiencia primaria. El inglés sigue como estándar para contribución y documentación técnica.

### Formato

Cada documento usa esta estructura:

```markdown
# Título del documento / Document Title

## ES

[ contenido en español ]

---

## EN

[ English content ]
```

La línea `---` (divisor de sección) separa el contenido ES del EN.

### Reglas para contenido en español

1. **Voseo neutro**: Usá "vos" para segunda persona singular informal, pero mantené un tono profesional. No usar regionalismos argentinos específicos (como "che" como muletilla).
2. **Tecnología en inglés**: Nombres de plugins, commands, variables de entorno, paths — siempre en inglés.
3. **Código en inglés**: Comments en código, nombres de funciones, identificadores — siempre en inglés.
4. **Consistencia con el código**: Si un keymap tiene descripción en español en `mappings.lua` (ej: "Salir de modo inserción"), usá esa misma descripción en los docs.

### Cómo contribuir traducciones

1. **Encontrá el archivo a traducir** en `docs/`
2. **Verificá que tiene la estructura bilingüe** (buscá `## ES` y `## EN`)
3. **Traducí solo la sección EN** si el contenido ES ya existe, o viceversa
4. **Mantené el mismo nivel de detalle** — no resumir una sección más que la otra
5. **Evitá traducir nombres de archivos, paths, commands** — estos siempre van en inglés
6. **Probalo**: si hay un test associated, corrélos

### Secciones obligatorias en cada doc

- `## ES` — contenido en español
- `## EN` — contenido en inglés
- `---` — divisor entre secciones
- Título en ambos idiomas (primero ES, después EN en el título)

### Ejemplo de estructura

```markdown
# Título del Doc / Doc Title

## ES

Contenido en español. Referencia a plugins como `codecompanion.nvim`
en inglés. Commands como `:Lazy sync` en inglés.

---

## EN

English content. Reference plugins like `codecompanion.nvim`
in English. Commands like `:Lazy sync` in English.
```

### Why bilingual

This project uses Spanish-English bilingual documentation (ES/EN). Spanish comes first because it reflects the maintainer's native language and primary audience. English follows as the standard for contribution and technical documentation.

### Format

Each document uses this structure:

```markdown
# Document Title / Título del documento

## ES

[ Spanish content ]

---

## EN

[ English content ]
```

The `---` (section divider) separates the ES content from the EN content.

### Rules for Spanish content

1. **Neutral voseo**: Use "vos" for second person singular informal, but keep a professional tone. Avoid Argentine regionalisms (like "che" as filler).
2. **Technology in English**: Plugin names, commands, environment variables, paths — always in English.
3. **Code in English**: Comments in code, function names, identifiers — always in English.
4. **Consistency with code**: If a keymap has a Spanish description in `mappings.lua` (e.g.: "Salir de modo inserción"), use that same description in the docs.

### How to contribute translations

1. **Find the file to translate** in `docs/`
2. **Verify it has the bilingual structure** (look for `## ES` and `## EN`)
3. **Translate only the EN section** if ES content already exists, or vice versa
4. **Keep the same level of detail** — don't summarize one section more than the other
5. **Avoid translating file names, paths, commands** — these always go in English
6. **Test it**: if there's an associated test, run it

### Mandatory sections in each doc

- `## ES` — Spanish content
- `## EN` — English content
- `---` — divider between sections
- Title in both languages (ES first, EN second in the title)
